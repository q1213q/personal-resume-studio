# 访问变慢、代理与照片质量排查

用户说“刚才好好的，现在变慢了”时，先保留当前版本、原图和症状，不立刻换平台、重复发布或压低照片质量。先找慢在哪一段，再选择影响最小的改法。

## 1. 确定可比较的基线

记录同一个实际公网 URL、部署版本、设备、浏览器、网络、视口、缓存状态与测试时间。区分首次访问和再次访问。只比较了不同网址或不同内容，不能把差异直接归因于网络或优化。

分别观察：

- 页面与关键资源请求：连接／TLS、首字节、下载耗时、失败与重试。
- 图片：文件到达、解码、CSS 遮罩加载，以及屏幕上真正可见的时间。
- 脚本：长任务、重复初始化、布局抖动、离屏后仍运行的帧循环。
- 动画：内容是否已加载却被刻意隐藏，固定开场时间是不是被误认为加载慢。

有限开场结束后应进入稳定阅读；网络慢时也给可读内容。不要等待所有无限动画结束才判定网站可用。

## 2. 区分网络与浏览器路径

用浏览器网络面板或可用浏览器工具观察真实访问；命令行测量只作为独立证据。CLI 与浏览器不一定使用相同代理，尤其系统代理和环境变量代理不同，不能用一次 curl 很快推断用户浏览器也快。

若证据指向代理，可在允许的独立测试浏览器／临时网络上下文中对照代理和直连，保持同 URL、版本与缓存条件；不擅自关闭用户全局代理、VPN、防火墙或证书校验。不适合自动测试时，把已经取得的证据说清，再请用户只做必要的网络对照。

出现明确网络差异时，检查代理路由、DNS、连接与服务可用性，不把图片当作唯一原因。在合理次数内复测，几次相近测量已足够时停止；不同地区、运营商、时段不能靠一台电脑替代。

## 3. 确认瓶颈后再优化

| 证据 | 优先行动 | 验证方式 |
| --- | --- | --- |
| 请求失败／首字节慢而文件小 | 检查域名、代理、线路和托管状态 | 同版本、不同网络路径对照；保留失败状态 |
| 请求数量多、重复文件 | 移除无用资源，复用依赖，合理缓存 | 查看瀑布图与请求数，确认路径未断 |
| 人像已下载但仍不可见 | 检查 decode、遮罩、样式和入场状态 | 截图／肉眼检查实际渲染，而非只看 `img.complete` |
| 图片确实占主要传输时间 | 尊重质量偏好，考虑延后加载非首屏图片、减少重复加载 | 先对照画质与体积，再检查实际加载 |
| 图片质量被破坏 | 找回原文件并替换正确展示路径 | 原图／发布包／线上字节与画面对照 |
| 内容加载好却很晚出现 | 缩短不必要等待，解码超时后回退可读内容 | 看实际可读时间与动画节奏 |
| 装饰退场后仍卡顿 | 停止帧循环、监听器、后台计算 | 离屏、暂停、后台切回检查 |

原始照片永远保留。生成展示副本应记录尺寸、格式和用途；用户已明确拒绝压缩时，不再偷偷改成低清 WebP／JPEG。遵守用户认可的质量要求；遮罩如需转换也要保持透明通道并检查边缘。不要删除 CSS 遮罩以换速度却破坏既定构图。

首屏图片按实际布局选择加载优先级，后续非关键图片可延迟加载。字体缺失时保证回退可读。合并或内联 CSS／JS 有减少请求和失去独立缓存的权衡，先测再决定；不把所有网站强制改成一个 HTML 文件。

## 4. 如实报告结果

记录更改前后同条件的耗时、文件大小、原图哈希、成功／失败请求及肉眼效果。功能通过、文件一致、单网速度正常和跨网可用是不同结论。

首次失败要保留原因与修复后的针对性复测，不删除失败结果再声称一直正常。只做手机尺寸模拟时明确标为模拟，不能声称已在真实 iPhone、安卓或微信内置浏览器验证。没有足够证据时说“当前这条测试路径正常，用户网络仍待验证”，不宣称已经解决所有地区的网络问题。

提交当前稳定版本和真实公网链接，说明画质是否保持、已修的问题与仍需观察的部分。除非用户请求持续监控，不自动创建定时任务。
